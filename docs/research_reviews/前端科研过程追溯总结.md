# EMG–IMU Human-in-the-loop 项目前端科研过程追溯总结

## 证据范围

本总结只讨论前端如何接收上游状态、组织音乐与视觉反馈，以及它在 Human-in-the-loop 中承担什么作用，不把采集协议、分类模型或跨日实验归为前端成果。

`muscle_music` 目录本身没有 Git 历史，因此无法根据 commit 准确恢复每次修改的作者和时间。下面的顺序主要依据现有代码、文档的新旧矛盾、文件时间和本线程中的讨论恢复。凡是只能证明“当前存在”、不能证明“何时由谁提出”的地方均明确说明。分类仓库虽然有 Git，但当前还有较多未提交修改，因此其内容只能作为目前的上游接口依据。

本次复核中，前端相关的 22 项自动测试全部通过，浏览器脚本语法检查通过。这说明协议解析、状态切换、音乐规则和异常处理的代码级行为基本一致，但不能替代真人体验、端到端延迟和误触实验。

## 一、前端研究问题是怎样变化的

前端最开始想解决的是：把手环识别出的动作映射成音乐控制，让没有音乐基础的用户也能通过简单手势逐步完成一段作品。早期方案默认手环可以同时提供 EMG 和 IMU 信息，用户能够通过食指捏合开始和结束，还能先用放松、握拳完成强度标定。旧版演示流程仍保留了这些设想，见 [DEMO_RUNBOOK.md](../../muscle_music/docs/DEMO_RUNBOOK.md#L3)。

后续确认当时接到前端的设备只有 200 Hz 六轴 IMU，不能可靠判断捏合、握力和肌肉激活。原来的交互假设因而不成立。团队没有继续用界面模拟这些能力，而是把第一版收缩为六个方向和相对运动强度，开始和结束改用页面按钮。这一边界已经写入 [README.md](../../muscle_music/README.md#L3) 和 [PROTOCOL.md](../../muscle_music/docs/PROTOCOL.md#L28)。这不是简单删功能，而是一次研究目标修正：先保证前端反馈建立在传感器真实可观测的信息上。

随后又发现，前端如果把采样率、置信度、运动强度、混音参数和内部状态全部放在主页面，虽然方便开发，却不能让体验者直观理解自己正在创造什么。前端的目标因此从“展示分类结果和系统参数”变成“让用户立即看见自己的动作加入了哪个声部、音乐何时变化、作品如何逐步形成”。当前主界面以生成画布、当前动作和六个声部为中心，连接信息及混音台默认收起，见 [index.html](../../muscle_music/demo/index.html#L29) 和 [index.html](../../muscle_music/demo/index.html#L76)。

现在更准确的前端研究问题是：上游状态存在延迟、不确定性和阶段变化时，前端如何把它转成及时、稳定、可理解的音乐与视觉反馈，让用户能够据此调整下一次动作。前端不负责判断人做了什么，而是研究机器的判断怎样重新作用于人，从而闭合交互回路。

## 二、主要决策链

### 1. 从理想交互退回到真实可观测能力

早期流程把捏合、握拳标定和 EMG 表达量当作现成输入。设备信息确认后，这些输入无法由当时的纯 IMU 稳定提供。最终方案保留接口兼容，但前端只实际使用方向和运动强度，第五个连续量被明确标为保留字段并忽略，见 [serve_demo.py](../../muscle_music/serve_demo.py#L35)。

这次修改属于科研假设变化，不只是工程修复。它形成了一个前端原则：不把硬件不能可靠观测的量展示成用户可以控制的功能。现在项目已经重新具备 EMG–IMU 分类后端，但前端尚未完成相应升级，因此不能把旧的纯 IMU 页面说成完整的 HumanState 前端。

### 2. 从参数面板改为可感知的音乐反馈

初版界面更接近调试仪表盘，用户需要阅读状态、强度、动态、连奏、复杂度和混音信息。本线程中 Boyan 明确指出这些信息对现场用户大多无用，要求用户在动作发生时直接看到自己生成了什么音乐。当前版本据此把六种声音设计成不同的视觉形态，并把技术信息收进设置区。方向与声部的固定关系写在 [app.js](../../muscle_music/demo/app.js#L18)，当前主页面结构见 [index.html](../../muscle_music/demo/index.html#L38)。

这项修改既是界面重构，也是对 Human-in-the-loop 的重新理解：主界面首先要帮助用户建立“动作—系统理解—反馈结果”的因果感，而不是证明后台有很多参数。目前只能证明这一设计已经实现，尚无用户实验能够证明它确实降低了学习时间或提高了控制感。

### 3. 把视觉即时性和音乐节拍稳定性拆开

如果动作一识别就立即替换乐句，声音会落在任意节拍位置；如果始终等到小节边界才有任何变化，用户又可能认为系统没有响应。当前方案在动作稳定确认后立即触发视觉动画，但把首次加入安排到下一拍，把已有声部的变化安排到下一小节，见 [app.js](../../muscle_music/demo/app.js#L994)。

前端还设置了 120 ms 的稳定确认、允许方向不经过无动作直接切换，并在约 1.5 秒没有输入时退出控制状态但不停止音乐，见 [app.js](../../muscle_music/demo/app.js#L891) 和 [serve_demo.py](../../muscle_music/serve_demo.py#L85)。这些机制解决了状态抖动、直接转向和掉线后的基本安全问题。

不过这里也暴露出新的问题：前端的 120 ms 使用浏览器收到数据的时间，而不是包中的源时间戳；上游分类器本身也已经有方向、手势和阶段状态机。两层稳定机制可能增加延迟，网络抖动也可能影响前端判断。目前没有 P50/P95 端到端测量，不能声称这一参数已经最优。

### 4. 从随机声音触发改为受约束的主题发展

项目曾担心重复进入同一方向后，音乐虽然变了，但用户听不出变化；如果每次完全重新生成，又会失去作品连续性。当前方案固定一首作品内的主题种子，让同一声部依次经历基础动机、节奏变化、装饰发展和高潮变化。所有音符仍受调性、和声、音域和密度约束，见 [MUSICAL_DESIGN.md](../../muscle_music/docs/MUSICAL_DESIGN.md#L3)。六轨同时出现时，系统减少弱拍装饰并自动降低拥挤声部，底鼓出现时短暂压低贝斯、和弦和环境，见 [app.js](../../muscle_music/demo/app.js#L262) 和 [app.js](../../muscle_music/demo/app.js#L1084)。

自动测试证明生成结果位于规定音阶和音域内，同一主题再次发展时确实发生变化，关键强拍仍保留和弦音，见 [test_music.py](../../muscle_music/tests/test_music.py#L20)。这些证据只能支持“规则没有越界”和“程序产生了差异”，不能支持“音乐一定悦耳”或“不同用户能够听出个性”。文档提出的随机基线、仅约束基线和完整系统三组盲听尚未实际完成，见 [MUSICAL_DESIGN.md](../../muscle_music/docs/MUSICAL_DESIGN.md#L15)。

### 5. 上游已经进入 HumanState，前端仍停留在旧协议

分类端目前定义了 `HumanState={D,H,A,P,M,C,Q}`，并通过 `/emgimu/state/v2` 输出方向、手势、双阶段、激活、运动强度、一致性、分项置信度和信号质量，见 [state.py](../../emgimu_classifier/src/emgimu/state.py#L100) 和 [OSC_V2.md](../../emgimu_classifier/docs/OSC_V2.md#L9)。

但浏览器中继仍只接受旧 `/emgimu/state` 的五个字段，前端也只读取一个 `confidence`。更严重的是，分类端为了兼容旧前端，会把 Direction 的 Unknown 和 None 都映射为 0，见 [state.py](../../emgimu_classifier/src/emgimu/state.py#L162)。这意味着当前前端无法区分“用户确实没有动作”和“机器看不清”，也无法知道是方向不可靠、手势不可靠还是信号质量有问题。

因此，整个系统的分类思想已经从平铺动作分类发展到 HumanState estimation，但前端还没有完成这次演变。当前最重要的前端任务不是继续增加动画，而是接入 v2 语义，并研究不确定性应如何反馈给用户。

## 三、工程实现与研究判断

工程实现主要包括：OSC 数据经本地中继转为浏览器 SSE；输入范围检查和掉线检测；方向状态稳定确认；六轨音乐生成、自动混音和浏览器音色；即时视觉动画、节拍显示、键盘模拟和自动演示。这些能力已经有代码和自动测试支持。

研究判断主要有四项。第一，前端只能使用传感器或分类端能够可靠提供的状态。第二，用户主界面应表现音乐变化，不应成为开发监控台。第三，视觉确认可以即时发生，而较大的声音变化应服从音乐时间。第四，变化必须在稳定映射和音乐约束中发生，不能用随机性代替个性化。

前端没有设计 D/H 标签、28 组合采集、跨 session 划分、EMG 归一化或分类模型。这些属于采集和分类模块。前端对应的职责，是完整保留这些状态的语义，特别是 Unknown、分项置信度、阶段和信号质量，并观察用户如何根据反馈修正动作。

## 四、Failure / Iteration Log

**原假设：** 捏合、握拳标定和 EMG 表达量可以直接进入首版交互。  
**实际结果：** 当时进入前端的设备只有六轴 IMU，相关量不可可靠观测。  
**新的解释与修改：** 先做方向和相对运动强度，开始结束改用按钮。  
**证据边界：** 可以确认当前代码和文档已经这样实现；无法从 Git 确认具体修改者和精确提交时间。

**原假设：** 展示更多输入和系统参数有助于用户理解。  
**实际结果：** 本线程评审认为信息过多，用户看不到动作真正改变了什么。  
**新的解释与修改：** 主界面改为生成画布，技术数据默认折叠。  
**证据边界：** 可以确认 Boyan 提出了问题、现有页面落实了方向；尚无真人对照实验验证效果。

**原假设：** 动作触发音乐变化即可形成好的交互。  
**实际结果：** 进一步讨论发现，立即改音可能破坏节拍，等待小节又削弱反馈感；完全随机变奏也不利于悦耳度和主题连续性。  
**新的解释与修改：** 即时视觉确认、节拍边界更新音乐、同主题分阶段发展。  
**证据边界：** 程序规则和自动测试成立，但悦耳度、个性化感和动作反馈感尚未通过用户实验验证。

**原假设：** 一个方向编号、一个总置信度足够驱动前端。  
**实际结果：** 新分类端已经将状态拆成 D/H/A/P/M/C/Q，并明确区分 Unknown 与 None。旧接口会丢失这些信息。  
**新的解释与修改：** 应让前端直接消费 v2 HumanState，并针对不同状态采取不同反馈策略。  
**证据边界：** 接口缺口已经由代码确认，但 v2 前端及其用户实验尚未实现。

## 五、HumanState 对前端意味着什么

`D` 是机器判断手臂向哪里运动，当前前端已经用它选择六个音乐声部。`H` 是手部姿态，当前浏览器版本未接入；未来更适合承担明确的确认或模式切换，而不应与方向组合成 28 个前端命令。

`A` 是相对肌肉激活程度，可以连续调节声音表达，但不是肌力。`M` 是相对运动强度，当前已经用于力度、明亮度和节奏密度，但不是位移或机械功率。`P` 表示动作处于 onset、active、hold 还是 release，应帮助前端决定何时预反馈、何时正式触发、何时结束保持；当前前端只有自己的 120 ms 稳定逻辑，没有使用上游阶段。

`C` 表示 EMG 与 IMU 在同类动作条件下是否呈现异常关系。第一版只适合诊断，不应覆盖 D/H 或直接向普通用户报警。`Q` 表示机器对这些判断有多相信，应至少区分 qD、qH 和阶段置信度，并结合 EMG/IMU signal quality。当前前端只有一个总置信度，因此仍不完整。

这些变量不能成为七个并列开关。D/H 是机器认为人在做什么，A/M 是观察到活动有多强，P 依赖历史，C 依赖跨模态条件，Q 则修饰前面所有判断。对前端而言，最重要的是按依赖关系制定反馈策略，而不是把七个数全部显示出来。

## 六、前端目前使用的人体与交互先验

已经用于前端的先验包括：动作具有连续性，短时跳变不应立即触发；方向适合选择稳定的结构含义；运动强弱适合控制连续音乐表达；用户需要即时确认，但音乐的大变化需要落在节拍边界；同一动作应保持同一声部含义，重复动作只发展主题。

分类端已经实现、前端尚未消费的先验包括 D/H 分离、Open 的短时记忆、双阶段状态、Unknown 拒识和按模态划分的信号质量。EMG 与 IMU onset lag、跨模态一致性目前更接近待验证研究假设。绝对肌力、手部三维位置和完整关节动力学受当前硬件限制，前端不能宣称能够反馈这些量。

这些先验都应作为可验证的软约束。比如 120 ms 只能作为待比较的交互参数，不能因为它写进代码就认为所有用户和动作都适用。

## 七、实验严谨性与下一步验证

上游已经把数据划分从随机窗口转向 trial、session/day、participant，并要求报告 macro-F1、混淆矩阵、ECE、coverage、risk–coverage 和 P50/P95 延迟。这些不是前端提出或完成的工作。前端需要做的是让相同的严谨性延伸到闭环评价：不能只看分类 accuracy，还要看一次动作是否造成正确的反馈、无意动作每分钟触发多少次、Unknown 后用户多久能恢复、从人体动作到视觉和声音改变的端到端延迟，以及用户是否理解系统为什么没有响应。

当前前端已有 22 项自动测试，但没有正式用户研究，也没有真实端到端延迟数据。最值得优先做的实验是完成 OSC v2 接入后，对三种反馈策略做对照：直接响应单帧结果；使用当前前端 120 ms 稳定确认；使用上游 P 与分项 Q，由前端只做最小防抖。比较误触、漏触、P50/P95 响应时间、Unknown 后恢复时间和主观控制感。这个实验能够回答前端是否真的改善 Human-in-the-loop，而不只是让页面更漂亮。

悦耳度应作为第二项独立实验，按文档已有设想比较随机生成、只有音乐约束、动作个性化三种版本。当前证据尚不足以把“悦耳”和“个性化”写成已经验证的成果。

## 八、三部分的接口关系

采集端负责让机器可靠地看见人，保存真实时间、质量和实验语义。分类端负责让机器理解人，把 EMG/IMU 转换为 HumanState。前端负责把这种理解以用户能感知的方式重新作用于人，并观察用户是否会根据反馈调整动作。

因此前端和上游之间最合适的边界是 HumanState，而不是原始 EMG/IMU，也不是已经压扁成一个手势编号的旧接口。前端可以决定反馈映射、节拍量化、显示层级和交互状态，但不应重新发明分类标签，也不应私自把 Unknown 当成无动作。

## 九、Boyan 的 ownership 证据

能够从本线程明确确认的有三件事。Boyan 在确认设备为 200 Hz 纯 IMU 后，要求前端按真实端口和硬件能力更新，没有继续宣传当时无法观测的捏合和肌力。Boyan 主动指出旧页面信息过多，要求用户直接看到自己正在生成的音乐，这推动了主界面从状态面板转为生成画布。Boyan 还连续追问重复动作的可听差异、音乐悦耳度和个性化，促使方案从简单的方向触发发展为主题演化、音乐约束和自动混音。

无法确认的部分也需要保留。`muscle_music` 没有 Git 历史，无法证明哪些代码由 Boyan 亲自编写；分类仓库提交作者显示为 `Zoker`，但仓库内没有证据证明该账号与 Boyan 的对应关系；也没有材料能够证明 Boyan 设计了采集端的 28 组合协议或分类端的全部 HumanState 方案。因此这些内容不应写成个人贡献。

# 给胡旭晖老师的 5–8 分钟汇报素材

老师，我负责的前端不是重新做分类，而是研究上游对人体状态的判断怎样反馈给用户，最终形成一个闭环。我们目前经历了四次比较关键的调整。

第一，最开始我们按理想方案设计了 EMG–IMU 多手势交互，设想用捏合开始、握拳做标定，方向控制音乐。后来接入时确认当时前端实际只有 200 Hz 六轴 IMU，捏合、握力和肌肉激活都不能可靠得到。我当时认为，如果继续在界面里保留这些功能，演示会建立在不存在的数据上。因此第一版主动收缩为六个方向和相对运动强度，开始结束改用页面按钮。这个变化让我意识到，前端首先要尊重传感器的可观测边界。

第二，早期页面像一个开发仪表盘，包含识别结果、置信度、运动强度、动态、连奏、复杂度和混音台。我发现用户即使看到这些数值，也很难理解自己的动作创造了什么。因此我们把主界面改成实时音乐画布：鼓、环境、和弦、旋律、琶音和贝斯分别有不同视觉形态，动作确认后画面立即响应，技术数据默认收起。这里的判断是，Human-in-the-loop 的前端不是显示更多数据，而是让用户理解动作与结果之间的关系。这个设计已经实现，但尚未通过正式用户实验验证。

第三，我们遇到了反馈速度和音乐稳定性的冲突。动作后立刻改音乐容易破坏节拍，等到下一小节又会让人误以为系统没反应。因此我们把两种反馈拆开：视觉立即确认，音乐在下一拍或下一小节进入。输入还设置了 120 ms 稳定确认和掉线复位。当前测试证明代码行为符合预期，但我们还没有测完整链路的 P50/P95 延迟，也没有证明 120 ms 是最佳值。这是下一步应当用实验回答的问题。

第四，重复挥向同一方向时，如果每次都随机生成，作品会失去主题；如果几乎不变，用户又感受不到自己的参与。后来我们改为同一主题的四级发展，并用调性、和声、音域和密度限制保证基本音乐性，再用自动混音控制六轨拥挤。自动测试已经证明音符不会越出规则，重复动作会产生变化，关键结构音会保留。但这只能证明程序满足音乐规则，不能证明真人认为它悦耳或有个性，盲听实验还没有做。

目前最大的前端问题不是视觉还不够丰富，而是上游已经升级为完整 HumanState，前端却仍使用旧五字段协议。旧协议会把 Unknown 和无动作合并，也只有一个置信度，接不到手势、阶段和信号质量。这样用户看不到机器是在说“你没有动作”，还是“我看不清”。所以下一步我最想先接入 v2，然后比较单帧响应、120 ms 防抖和基于阶段与分项置信度的反馈策略，用误触、漏触、端到端延迟、恢复时间和主观控制感判断哪一种真正适合闭环。

## 最值得导师记住的三件事

1. 前端的目标已经从显示分类结果转为构建可理解、可修正的 Human-in-the-loop 反馈。
2. 项目主动按硬件可观测能力收缩功能，并用即时视觉与节拍化声音分别解决反馈感和音乐稳定性。
3. 当前最大的缺口是前端尚未接入完整 HumanState，尤其无法区分 Unknown 与无动作；这比继续增加动画或手势更优先。

## 最值得向导师请教的三个开放问题

1. 当系统不确定时，前端应该安静地不执行，还是明确告诉用户“没有识别清楚”？怎样既避免误导，又不打断演奏？
2. 动作应该在 onset 阶段就给出反馈，还是等到 stable/active 后再执行？允许多大延迟才能换取较低误触？
3. 固定的“方向—声部”映射更容易学习，个性化映射更有表达力。第一阶段应如何设计对照实验，判断两者对控制感和创作感的真实影响？
